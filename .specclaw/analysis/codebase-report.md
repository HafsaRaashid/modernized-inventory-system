## Structure/Architecture

The README (`README.md`, discovered doc) states: "The project follows a **classic Windows Forms architecture**, where each screen is represented by its own Form (`frm*.cs`)." I confirmed this by opening multiple `frm*.cs` files directly: `frmGiris.cs` (login screen, class name `GİRİŞ_EKRANI`), `frmAnaMenu.cs` (main menu / navigation hub), `frmAdmin.cs` (admin panel), `frmDemirbasIslem.cs` (asset-to-room assignment operations), `frmStokEkleme.cs` (stock/asset-type entry), and `frmRapor.cs` (reporting/printing). Each form is a monolithic `partial class ... : Form` that mixes UI event handlers directly with inline SQL data access — there is no separate service, repository, or data-access layer. For example, `frmDemirbasIslem.cs` defines `VTbaglan()`/`VTkapat()`/`GuncelleAdet()`/`dgwOdaDoldur()` etc. as instance methods directly on the form class, and `frmAnaMenu.cs`'s `btnOdaDemirbas_Click` directly does `frmDemirbasIslem frmdemirbasislem = new frmDemirbasIslem(); frmdemirbasislem.Show(); this.Hide();` — navigation between screens is done by each form showing/hiding the next, not through a router or shared navigation service.

Every data-access form redundantly redefines its own `VTbaglan()`/`VTkapat()` pair with an inline, hardcoded connection string (identical string literal appears in `frmGiris.cs`, `frmAnaMenu.cs`, `frmDemirbasIslem.cs`, `frmStokEkleme.cs`, and `frmRapor.cs`) rather than centralizing connection management or reading from `App.config`'s `<connectionStrings>` (which, per my reading of `App.config`, contains no `<connectionStrings>` section at all — only a `<startup>` block).

The single `UnitTestProject1/UnitTest1.cs` test file only exercises `Test1.cs`'s `FiyatDogruMu`/`IsNumeric` helper methods (price-string validation) — it does not test any form or database logic. ## Risks/Tech-Debt

**SQL injection via string concatenation in authentication and reporting code.** `frmGiris.cs`'s login handler builds its query as `"SELECT COUNT(*) FROM tblKullanicilar WHERE KullaniciAdi='" + kAdi+ "' AND Sifre='" + sifre + "'"` directly from unescaped `txtUsername.Text`/`txtPassword.Text` — a classic SQL-injection-based authentication bypass vector. The same pattern recurs in `frmAnaMenu.cs`'s authorization check (`"SELECT YetkiID FROM tblKullanicilar WHERE KullaniciAdi='" +k + "' AND Sifre='" + s + "'"`) and in `frmRapor.cs`'s report query (`"...WHERE OdaAdi='" + oda + "'"`, built from a combobox value). By contrast, the insert/update statements in `frmDemirbasIslem.cs` and `frmStokEkleme.cs` correctly use parameterized `SqlCommand.Parameters.AddWithValue`, showing the team knows the safe pattern but did not apply it consistently, especially in the security-critical login path.

**Hardcoded, duplicated production-shaped credentials.** The literal connection string `"server=localhost,1433;Initial Catalog=DemirbasTakip;User Id=sa;Password=DemirbasDev!2026;TrustServerCertificate=True"` is hardcoded identically inside at least five separate form source files (`frmGiris.cs`, `frmAnaMenu.cs`, `frmDemirbasIslem.cs`, `frmStokEkleme.cs`, `frmRapor.cs`) rather than being centralized in `App.config`'s `<connectionStrings>` (which I opened and confirmed is absent — `App.config` only contains a `<startup>` element). It uses the SQL Server `sa` superuser account with a plaintext password committed to source control, and any credential rotation requires editing every form file individually.

**Passwords stored/compared in plaintext.** `frmGiris.cs`'s login query compares `Sifre='" + sifre + "'"` directly against user input with no hashing visible in the code I read — combined with the SQL string concatenation above, this is a compounded authentication risk.

**Broken/missing third-party dependency.** `YazılımSınamaProjesi.csproj` references `itextsharp` via `<HintPath>..\itextsharp.dll</HintPath>`, but I confirmed by direct filesystem check that no `itextsharp.dll` exists at that path in this checkout — the project will not build cleanly from a fresh clone without manually sourcing this DLL, and there is no NuGet manifest to restore it automatically.

**Checked-in database files.** `DemirbasTakip.mdf` and `DemirbasTakip_log.ldf` (SQL Server primary data file and transaction log) appear directly in the repository's `top_level_dirs`, alongside build artifacts (`bin/`, `obj/`) — binary database state and build output are versioned in source control rather than excluded via `.gitignore`.

**Thin, narrowly-scoped test coverage.** The only test file, `UnitTestProject1/UnitTest1.cs`, contains three `[TestMethod]`s (`IsPrıceTrue`, `IsEmpty`, `IsInvalid`) that exercise only `Test1.cs`'s `FiyatDogruMu` price-string validator. None of the forms' data-access logic, SQL queries, or navigation flow have any test coverage, and the collected facts confirm no dedicated test directory exists inside the main app (`test_locations: []`).

**Duplicated data-access boilerplate.** Every form re-implements its own `VTbaglan()`/`VTkapat()` connect/close pair and inline SQL rather than sharing a common data-access class — confirmed by comparing the identical method bodies across `frmGiris.cs`, `frmAnaMenu.cs`, `frmDemirbasIslem.cs`, `frmStokEkleme.cs`, and `frmRapor.cs`. This means any change to connection handling (e.g., adding retry logic, moving the connection string to config) has to be repeated in every form file.

## Suggested First Changes

- **Start with `frmGiris.cs`'s `button1_Click` handler** — it is the single highest-risk entry point (SQL-injection-vulnerable login query combined with the hardcoded `sa` credential and plaintext password comparison I quoted above) and is also the literal first screen the app shows (per `Program.cs`'s `GİRİŞ_EKRANI giris = new GİRİŞ_EKRANI(); giris.Show();`). Replacing the concatenated query with a parameterized `SqlCommand` (as already correctly done in `frmDemirbasIslem.cs`'s insert statement) would be a small, self-contained, high-value fix.
- **Centralize the connection string** by adding a `<connectionStrings>` section to `App.config` (currently absent — I opened the file and confirmed it only has a `<startup>` block) and refactoring the five duplicated `VTbaglan()` methods I found in `frmGiris.cs`, `frmAnaMenu.cs`, `frmDemirbasIslem.cs`, `frmStokEkleme.cs`, and `frmRapor.cs` to read from it via `ConfigurationManager.ConnectionStrings`, removing the hardcoded `sa` password from source.
- **Resolve or remove the broken `itextsharp` reference** in `YazılımSınamaProjesi.csproj` before attempting a clean build on a new machine — either restore the missing `itextsharp.dll` (perhaps via the modern `iTextSharp`/`itext7` NuGet package) or confirm it's unused and drop the reference; I found no other file referencing an `iTextSharp` namespace in the forms I opened, so this may be a vestigial dependency worth investigating with a full-project search before other work proceeds.
- **Expand test coverage beyond `Test1.cs`** — since `UnitTest1.cs` (the only test file, confirmed by the empty `test_locations` in the collected facts) covers only price-string validation, a newcomer wanting to safely refactor the data-access duplication above would benefit from adding tests around the SQL query construction (e.g., extracting the query-building logic in `frmDemirbasIslem.cs`'s `dgwOdaSecimiDoldur()` into a testable method before parameterizing it).
