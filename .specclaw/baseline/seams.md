## Excluded: UI Automation

WinForms `Form`-driven UI automation (e.g. simulating clicks/keystrokes through the actual rendered controls, or navigating between forms via `.Show()`/`.Hide()`) is excluded entirely, for two independent reasons:

1. **The rebuild target is a different platform and paradigm.** SQ-001 (clarifications.md) settled the rebuild target as a web application (ASP.NET Core Web API + React/TypeScript SPA), replacing this WinForms desktop app entirely. A WinForms `Form`-driven UI test (`SendKeys`, `Control.PerformClick()`, a message-loop pump) exercises Windows message-loop/rendering machinery that has no counterpart in a browser-rendered SPA — no such test would carry forward into the rebuild's own UI test suite, and writing one now would be pure sunk cost. SQ-013 (FAITHFUL layout/theme fidelity) is a visual-parity commitment, verified separately by `/specclaw:bf-ui`'s screenshot workflow (already staged per SQ-013's own finding), not by this golden-master harness.
2. **Every business rule this app has is reachable at a lower-cost, higher-fidelity layer already.** Every `DR-###` rule and every extra behavior identified below is observable by calling the relevant `Form` method directly (via reflection where the method/control is `private`) with a live database arranged underneath it — the `service` class above. Driving the same rule through the real UI would additionally measure WinForms event wiring and rendering, at higher cost and no additional fidelity to the business rule itself.

## Capture Blockers (Determinism Audit)

1. **`DateTimePicker` controls default to `DateTime.Now`, unset in every Designer file.** `dtpAlimTarihi` (`frmStokEkleme.Designer.cs:45`), `DtmSGAlimTarihi` (`frmStokGuncelleme.Designer.cs:43`), and `dtmBilgi` (`frmAramalar.Designer.cs:40`) are all constructed with no explicit `.Value = ...` assignment anywhere in their respective Designer files — confirmed by a direct grep across all three. A WinForms `DateTimePicker`'s `Value` defaults to the wall-clock `DateTime.Now` at construction time.
   **Mitigation — Option 1 (record the capture timestamp / inject a fixed value):** every scenario touching `AlimTarihi` (Stock Add/Update) or the date-search branch (`frmAramalar`) must have the harness explicitly set the control's `.Value` (via reflection, since the control field is `private`) to a fixed, `anchor_date`-derived value during Arrange — never rely on the control's own load-time default. This costs nothing extra (the field must be set via reflection regardless, since there is no other way to feed input into a `private` control) and fully removes the non-determinism.
   **This should become a clarify TARGET-GAP question** if the rebuild's own date-input equivalent needs the same explicit-injection discipline — `clarifications.md` does not currently carry a question on this specific point.

2. **`ANA_MENÜ_Load`'s admin-gate query has no `ORDER BY`, and its result loop is last-row-wins.** `frmAnaMenu.cs:42-54`: `SELECT YetkiID FROM tblKullanicilar WHERE KullaniciAdi=... AND Sifre=...` returns zero or more rows with no `ORDER BY`; the `while (okuyucu.Read())` loop unconditionally reassigns `btnAdmin.Enabled` on every row it reads, so if more than one row matches the same username+password pair with different `YetkiID` values, the final result depends on the physical/index scan order SQL Server happens to choose — not on anything the code itself pins.
   **Mitigation — Option 3-equivalent (control the arranged input):** every DR-003 scenario in this design arranges **exactly one** matching `tblKullanicilar` row per username+password pair, sidestepping the ambiguity entirely; the multi-row case is *not* scenario'd (a fixture built from one arbitrary run's row-order result would misrepresent genuinely undetermined behavior as a pinned rule).
   **This is exactly a clarify TARGET-GAP question** — raised fresh this run as **PQ-011** (no existing PQ/CQ covers it; `clarifications.md` does not currently carry this question).

3. **Systemic: every multi-row `SELECT` in this codebase lacks an `ORDER BY`.** Confirmed by reading all eleven forms' query text directly — `dgwOdaDoldur()`, `dgwDemirbasDoldur()`, `dgwOdaSecimiDoldur()` (`frmDemirbasIslem.cs`), the Room/Personnel grid fills (`frmOdaTanimlama.cs`), every search branch (`frmAramalar.cs`), and the report query (`frmRapor.cs`) all return rows in whatever order SQL Server's query plan happens to produce.
   **Mitigation — Option 2 (normalize out of comparison):** any scenario whose Assert shape includes a multi-row list (Search results, Reporting results) has the harness sort captured rows by their own natural key (e.g. `DemirbasID`, `PersonelID`) **before** writing the fixture; row order itself is treated as excluded from comparison, full field-value comparison still applies per row.
   **This is a clarify TARGET-GAP question**, raised fresh this run as **PQ-012**; `clarifications.md` does not currently carry it.

4. **Auto-increment identity columns** (`OdaID`, `DemirbasID`, `PersonelID`, `OdaDemirbasAtamaID`, `DemirbasTuruID`, `DepartmanID`) are all server-generated. Per `CONTRACT.md` (k), every scenario below whose Act creates a new row captures **boolean/count assertions** (`row_created`, `row_count_after_delta`, etc.) as its primary Assert shape, not the raw generated id; where a raw id is genuinely part of the captured `output` shape, harness mode must list its path under that fixture's `normalized_fields`, never compare it directly. No numbered mitigation option applies here (this is (k)'s standard pattern, not a clock-style finding) — stated here so `--harness` mode does not have to re-derive it per scenario.

5. **No business rule in this codebase compares a stored date to "today."** Checked directly: `AlimTarihi` (purchase date) is stored and read back verbatim, never compared against `DateTime.Now`/`.Today` anywhere in any of the eleven forms opened this run. Option 1 (injectable clock for a business computation) is therefore **not** needed anywhere in this app — only Blocker #1 above (control-default capture) applies to dates here.

6. **`frmAramalar`'s date-search `LIKE` pattern's actual match behavior could not be confirmed from source alone.** `frmAramalar.cs:136`: `"...WHERE AlimTarihi LIKE '%" + dtmBilgi.Value.ToString("yyyy-MM-dd") + "%'"` compares an implicitly-converted `datetime` column against an ISO-formatted wildcard string. Whether SQL Server's implicit `datetime`→`varchar` conversion in this context actually produces `yyyy-MM-dd`-shaped substrings depends on the server's session language/`dateformat` settings, which this analysis cannot determine from source code alone. This is **not** flagged as a capture blocker requiring a mitigation choice — the harness simply records whatever actually happens (GM-043) as the ground truth, which is exactly what golden-master capture is for; noted here only so a `record`-time surprise (e.g. the date search never matching anything) is not mistaken for a harness bug.

## Recommended Seam

**Start capture with the pure-function class** (`Test1.FiyatDogruMu` first — zero setup, zero DB, already independently exercised by `UnitTestProject1`; then the keypress-filter methods, accounting for the `MessageBox.Show` suppression caveat above). Lowest cost, highest fidelity, and capturing these first de-risks the reflection-based invocation technique the rest of the harness depends on before any DB arrange step is added.

**The single highest-value target after that is the Asset Assignment composite flow** (`frmDemirbasIslem.btnDemirbasIslemKaydet_Click` / `GuncelleAdet()`, seam layer `service`) — it is the app's most stateful component (architecture.md L4), it is the only place DR-001 and DR-002 are pinned together as one Composite Flow (functional-spec.md), and it is also where the DR-001 guard is demonstrably *not* enforced at every call path (`GuncelleAdet()` is reachable directly — GM-040) — exactly the kind of fact a rebuild could silently lose without a golden-master fixture pinning it.

All remaining `service`-class seams (Room CRUD, Room Assignment, Stock CRUD, Search, Reporting, Login, Admin gate) are recommended next, in the order given in the Seam Ranking table above, since none requires anything the first two don't already establish (a live `tblXxx` arrange step, plus the reflection-invocation technique for private controls/handlers).
