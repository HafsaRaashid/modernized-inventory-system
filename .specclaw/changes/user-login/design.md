# Design: BL-001 — User Login (Authentication)

**Change:** user-login
**Created:** 2026-08-28

## Technical Approach

Add a `User` domain entity and a `Users` table (EF Core migration), a PBKDF2 password-hashing service and a JWT-issuing service in `InventoryTrackingSystem.Infrastructure`, and a thin `AuthController` in `InventoryTrackingSystem.Api` that wires them together behind `POST /api/auth/login`. On the frontend, a `Login` screen posts to that endpoint through a new `auth.ts` API module, and a small `AuthContext` holds the resulting token in memory + `sessionStorage`, finally wiring the api client's existing (currently no-op) `getAuthHeader()` seam.

No route-guard/authorization enforcement is added anywhere else — issuing the token is this change's whole job. No admin screen for managing `User` rows is built (CQ-012) — the only way a `User` row is ever created in this rebuild's scope is a future data migration, which is why this change does not seed or migrate the 9 legacy accounts itself, only builds the hashing primitive such a migration would use.

## Architecture

```
Login.tsx --submit--> auth.ts --apiFetch--> POST /api/auth/login
                                                   |
                                            AuthController
                                             /          \
                                  PasswordHasherService  JwtTokenService
                                             \          /
                                          AppDbContext.Users (EF Core, SQL Server)

On 200: AuthContext stores token (memory + sessionStorage)
        client.ts's getAuthHeader() now reads it -> Authorization: Bearer <token>
        App.tsx navigates "/" -> AppShell shows "Signed in as <username>"
On failure: Login.tsx shows the legacy failure message, resets both fields
```

## API Changes

`POST /api/auth/login`

- Request: `{ "username": string, "password": string }`
- 200: `{ "token": string, "username": string }`
- 401: `{ "error": "INVALID_LOGIN_CREDENTIALS", "message": "Hatalı giriş yaptınız. Lütfen tekrar giriniz!!!" }`

## Key Decisions

- **PBKDF2 over a NuGet identity package.** `Rfc2898DeriveBytes` is already in the BCL (`System.Security.Cryptography`) — no new dependency, and this system's scale (9 accounts, SQ-010) doesn't warrant pulling in ASP.NET Core Identity's full membership provider.
- **JWT over cookie sessions.** A stateless bearer token fits a SPA + Web API pair with no existing session store, and needs no new infrastructure (SQ-003: self-hosted, no cloud session backend). `System.IdentityModel.Tokens.Jwt` is added as an explicit package reference rather than relied on transitively (it currently appears in the build output only as a transitive dependency of `Microsoft.Data.SqlClient`'s Azure.Identity chain, which is not a contract this change should lean on).
- **`sessionStorage`, not `localStorage`.** Matches "session" semantics — the token doesn't outlive the browser tab being closed. Either is architecturally fine for this small system; this is a stated pick, not a security requirement.
- **`/` redirects to `/login` when unauthenticated; login navigates to `/`.** BL-002 (Main Menu) doesn't exist yet and is explicitly out of scope. `AppShell` stands in as the authenticated landing state until BL-002 replaces its content — this is a placeholder destination, not Main Menu itself, and is not this change's version of BL-002's scope.
- **TK-001's CSS values are a stated approximation.** `SystemColors.Highlight`/`ControlText`/`Control` are OS-theme-relative with no fixed RGB in source (`design-tokens.json`'s own note). `Login.css` uses common default-Windows-theme approximations (`--login-button-bg: #0078D4`, `--login-button-fg: #000000`, `--login-form-bg: #F0F0F0`) as a starting point, explicitly flagged for confirmation once a human captures a real screenshot and signs off `ui-review.md` — this is not a claim of proven visual fidelity.

## Risks & Mitigations

- **Risk:** the exact PBKDF2 iteration count/parameters, if under-specified, could be weak or non-standard. **Mitigation:** use OWASP's current recommended minimum (600,000 iterations, HMACSHA256, 128-bit salt) as the fixed default, stored per-hash so it can be raised later without breaking existing hashes.
- **Risk:** `Jwt:SigningKey` left empty in committed `appsettings.json` and never set locally would let the app start with an insecure/empty signing key. **Mitigation:** `JwtTokenService` throws at startup (not at first login) if the configured key is missing or shorter than 32 bytes — fails loud and early, matching the existing `ConnectionStrings:Default` pattern of "empty in git, required via user-secrets."
- **Risk:** no real production password data exists to validate the migration path end-to-end. **Mitigation:** explicitly out of scope (see spec.md Notes) — `PasswordHasherService`'s own round-trip tests are what's verifiable now; the actual migration is a future, separate, data-only step.
